Odin Architecture Restructuring Plan

A responsibility-first simplification of the hybrid C++/Python workflow harness.

Assessment date: 2026-08-31 · Scope: source, definitions, adapters, tests, configuration, and existing documentation

01Executive summary

Recommendation: restructure Odin, but do not rewrite it. The executable adapter boundary, data-driven workflows, durable run files, and parity testing are good foundations. The highest-value work is to establish one authoritative orchestration core, make persistence crash-consistent, separate installed runtime paths from project paths, and make adapter capabilities explicit.

The project is understandable at the feature level but harder to reason about at the ownership level. C++ and Python both contain a complete CLI and workflow engine; src/cli.cpp and src/engine.cpp each carry several unrelated responsibilities; runtime assets are found through the consuming project's configuration root; and declarative concepts such as agent reads/writes are not enforced.

The plan intentionally avoids introducing a large class hierarchy or a directory for every concept. Odin's existing free-function, plain-struct C++ style can remain. The simplification is primarily about reducing duplicate authority and giving persistence, stage execution, path resolution, and command handling clear owners.

02Project overview

Odin coordinates software-development tasks through JSON workflows. A task moves through agent, gate, checkpoint, and Git-staging stages. Each stage produces a handoff/v1 object, and the workflow routes according to approved, revision, or blocked.

C++ currently owns

  • Primary CLI parsing and dispatch
  • Configuration and definition loading
  • Workflow execution and durable state
  • Adapter and gate subprocess invocation
  • JSON serialization and atomic replacement
  • Python delegation and schema-sidecar lifecycle

Python currently owns

  • A second full CLI and workflow engine
  • JSON Schema validation
  • Provider and agent-CLI discovery
  • Credential storage and resolution
  • Optional tool installation
  • Provider transports and output recovery

Current runtime flow

03What to preserve

Restructuring should build around these strengths rather than replace them.

KeepAssessment
KEEP Executable adaptersThe one-request/one-handoff process contract is small, language-neutral, testable, and isolates provider dependencies.
KEEP Data-driven workflowsAgent, skill, workflow, and template JSON keeps product policy outside the engine. Validation needs strengthening, not replacement.
KEEP Filesystem stateHuman-readable state and events are useful for resume, diagnostics, and a GUI. The commit protocol needs to become explicit.
KEEP C++ core / Python edgeThe language split is sensible when C++ owns deterministic execution and Python owns discovery, credentials, schemas, and provider I/O.
KEEP Parity testingThe Python implementation is valuable as an executable specification while the C++ architecture changes.
KEEP Free-function C++ stylePlain structs and module-prefixed functions fit this project. Clear modules matter more than object-oriented abstractions.
Non-goal: this is not a proposal for microservices, a plugin framework, dependency-injection machinery, or a deep enterprise layering scheme. Odin is small enough to remain a compact executable plus Python runtime helpers.

04Architecture findings

The following findings combine the source review with the concerns already recorded in docs/odin-status.html. Severity reflects correctness and architectural leverage, not estimated coding effort.

Correctness and operational boundaries

CRITICAL Stage completion is not a transaction. An attempt is changed only in memory, external work runs, then the event, context, and state are written separately. An interruption can replay side effects and replace the same event sequence. src/engine.cpp:502-570
CRITICAL Benchmarks share a mutable workspace. Later model profiles observe changes made by earlier profiles, so comparative results are order-dependent. src/cli.cpp:330-386; harness/cli.py:358-383

05Restructuring principles

One owner per responsibility

C++ owns production orchestration. Python owns services that benefit from Python. The Python engine is a test oracle, not a second product.

Boundaries before folders

Define path, persistence, stage execution, and adapter contracts first. Move files only when ownership is clear and tests protect the move.

Typed core, JSON edges

Use plain C++ structs for known domain values. Keep arbitrary artifact bodies and wire payloads as JSON.

Journal is authority

Immutable events represent stage intent and completion. State and context are atomic, replaceable snapshots for fast reads.

Capabilities are explicit

A chat endpoint must not be selected for a workspace-writing stage. Validate the route before the run starts.

Compatibility is deliberate

Preserve shipped run data and process contracts through versioned readers or migrations, not permanent duplicate implementations.

Avoid architecture for its own sake. Do not create interfaces for the clock, filesystem, ID generator, and every helper immediately. Extract a boundary when it protects a real side effect, enables fault injection, or removes a concrete dependency from the engine.

Path model

struct runtime_paths
{
    fs::path runtime_root;      // installed executable and Python runtime
    fs::path definitions_root;  // schemas, workflows, agents, skills, templates
    fs::path project_root;      // consuming repository and gate working directory
    fs::path workspace_root;    // isolated tree used by the current run
    fs::path state_root;        // runs and benchmark reports
    fs::path credential_root;   // explicit project or user credential scope
    fs::path config_path;       // selected odin.toml
    std::string python;         // resolved interpreter
};

This one value should be constructed once by the CLI and passed to the modules that need paths. It removes repeated inference and makes a standalone installation testable.

Run commit model

1. Acquire the run lock.
2. Append a create-only stage-started event with attempt and execution IDs.
3. Persist a snapshot showing the stage as in progress.
4. Execute the external side effect.
5. Validate the handoff and append a create-only stage-completed event.
6. Apply the transition and atomically replace context/state snapshots.
7. Release the lock.

On resume, an unmatched stage-started event is visible as "interrupted" or
"outcome uncertain". It is never silently mistaken for an unattempted stage.

Existing v1 runs should remain readable. New runs can use a versioned event format, with a small v1 loader that preserves concrete persisted compatibility rather than preserving two engines.

Capability model

[adapters.local-chat]
capabilities = ["chat"]

[adapters.opencode]
capabilities = ["chat", "workspace-read", "workspace-write", "process"]

Agent or stage requirement:
requires_capabilities = ["workspace-read", "workspace-write", "process"]

Validate capability compatibility during start and validate. This turns an implicit prompt expectation into an enforceable routing rule.

Do not perform this as one mass move. The physical layout is an end state. Extract tested responsibilities first, then move language-neutral assets and Python modules after runtime path resolution no longer depends on their current locations.

Smallest useful C++ split

If the complete target feels too broad, the minimum high-value split is five additions:

  1. runtime_paths removes installation assumptions.
  2. run_store owns every run read/write and recovery rule.
  3. stage_executor removes process and Git details from the state machine.
  4. command_validate removes definition traversal from the CLI.
  5. benchmark owns workspace isolation and reporting.

This split is sufficient to make engine.cpp and cli.cpp substantially easier to read without creating an abstraction for every helper.

08Migration plan

PHASE 0

Freeze behavior and clarify documentation

Before moving responsibilities, turn existing behavior into an explicit baseline.

  • Add clean Windows and Linux CI builds and run the native, Python, and parity suites.
  • Expand CLI parity to compare stderr and successful start, resume, status, and benchmark cases.
  • Add engine parity cases for feature, bug-fix, revision, blocked, and intermediate resume paths.
  • Separate a required full gate from a Python-only gate; a missing native build must not appear as a full pass.
  • Mark the C++ port plan historical and correct README claims that contradict current behavior.

Exit: a clean checkout proves the compatibility baseline on every supported platform.

PHASE 1

Make execution safe

Correctness changes precede cosmetic restructuring because they define the boundaries later modules must expose.

  • Introduce a per-run lock and reject concurrent resume.
  • Implement started/completed journal records and create-only event writes.
  • Persist attempt identity before running an adapter, gate, or Git command.
  • Define recovery for an interrupted stage and expose it in status output.
  • Implement POSIX process-group termination and cancellation propagation.
  • Give Git staging a timeout and validate repository-relative paths.
  • Use explicit child environment policies and redact persisted diagnostics.

Exit: fault-injection tests prove that every interruption yields a diagnosable, resumable state without duplicate event replacement.

PHASE 2

Establish explicit roots and installation

  • Add runtime_paths and construct it once at startup.
  • Make project commands run in workspace_root, not an overloaded config.root.
  • Resolve schemas, definitions, adapters, and Python scripts from runtime_root.
  • Pass credential scope explicitly to Python adapters.
  • Add CMake install rules and an integration test with runtime, project, state, credentials, and workspace in different directories.

Exit: an installed Odin executable can operate on a separate consuming repository.

PHASE 3

Split overloaded modules

  • Extract all run persistence from engine.cpp into run_store.
  • Extract the four stage implementations into stage_executor.
  • Leave transition selection, limits, and orchestration in engine.
  • Extract validation and benchmark behavior from cli.cpp.
  • Centralize Python child lifecycle in python_runtime; use scoped cleanup rather than repeated manual stops.
  • Rename atomic_file to reflect its broader filesystem role, or split path/read helpers from atomic writing.

Exit: each source file has one sentence that accurately describes its responsibility.

PHASE 4

Remove production duplication

  • Create a minimal Python bootstrap CLI for doctor, auth, and tools.
  • Stop importing the Python engine and config stack when delegated commands start.
  • Move the Python engine, old CLI behavior, and reference runner under parity tests.
  • Share prompt rendering between the HTTP and CLI adapters.
  • Move schemas and definitions to a language-neutral installed asset directory.
  • Move repository-only scripts to tools; keep production sidecar code in the runtime package.

Exit: production has one engine and one command authority; Python reference code remains available only to tests.

PHASE 5

Make the declarative model real

  • Parse workflow stages and handoffs into typed C++ values after schema validation.
  • Add kind-specific workflow schema rules, unique stage IDs, graph checks, and artifact dependency checks.
  • Declare adapter capabilities and stage requirements; validate routes before execution.
  • Add stage-specific artifact contracts, especially for changed_files and verification evidence.
  • Enforce agent reads/writes by filtering inputs and validating outputs, or remove those fields.
  • Decide whether workflow IDs are extensible. If only feature and bug-fix are supported, simplify the generic claims; otherwise remove the schema enum restriction.

Exit: definitions describe behavior the runtime actually enforces.

12Acceptance criteria

The restructure is complete when these statements are true.

  • There is one production workflow engine and one authoritative primary CLI.
  • The Python reference engine is test-only and can be omitted from a production package.
  • An installed Odin operates on a project in another directory without source-tree assets beside odin.toml.
  • One run cannot be resumed concurrently by two processes.
  • An interruption leaves an explicit started/completed record and never silently replaces an event.
  • Existing v1 run directories remain readable or have a tested migration command.
  • Adapters and stages declare capabilities, and incompatible routes fail before execution.
  • No unvalidated model-provided path reaches Git.
  • Children receive only their allowed environment and required credentials.
  • Benchmark profiles begin from equivalent isolated workspaces.
  • Timeout and cancellation terminate process trees on Windows and POSIX.
  • engine.cpp contains transition orchestration, not Git, provider, or persistence mechanics.
  • cli.cpp contains argument handling and presentation, not benchmark or definition-validation implementations.
  • Workflow fields documented as contracts are enforced by validation or removed.
  • Windows and Linux full gates run from a clean checkout without silent skips.
  • README examples execute successfully as smoke tests.

13Recommended first implementation slice

The first code change should be small enough to review independently and useful even if later phases are delayed.

  1. Add clean CI and make the full gate require a native build.
  2. Add runtime_paths.h/.cpp without moving files yet.
  3. Populate runtime and project roots separately in cli_main.
  4. Change definitions, sidecar, delegation, adapters, state, and gate working directories to consume the appropriate explicit root.
  5. Add one installed-layout integration test where Odin assets and the sample project are separate.
  6. Update README invocation and installation guidance to match the tested layout.

This slice removes the most pervasive architectural ambiguity without changing workflow semantics or the adapter protocol. It also creates the path vocabulary needed by benchmark isolation, credentials, packaging, and future GUI work.

Do not begin with a repository-wide file move. Moving harness, scripts, and adapters before path ownership is explicit would create a large diff while preserving the same hidden coupling. First make locations configurable and tested; then move them mechanically.
