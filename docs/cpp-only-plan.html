Odin C++-Only Migration Plan

Port every shipped runtime responsibility to C++, then remove Python from the repository and build.

Direction confirmed: 2026-09-01 · Revised after source audit: 2026-09-01 · Python parity is not a product requirement

01Decision

Odin will become a C++-only product. The installed runtime, CLI, adapters, validation, discovery, credentials, tests, CI, and packaging must work without a Python interpreter. Existing Python code will not be refactored or extended during the migration. Each responsibility will be implemented independently in C++, switched over after native tests pass, and the Python tree will then be deleted.
Progress: phases 0 and 1 are done. The native test suite passes with no python on PATH (112/112), validate and every workflow stage run natively, the checked-in odin.toml executes a complete run with no interpreter, and 6 Python files are gone. The remaining Python is one block: doctor, auth and tools hold the whole harness/ tree alive through delegate.cpp, so nothing more can be deleted until those three are native.

This supersedes the earlier hybrid and parity-oriented plans. Exact Python output, exception text, key ordering, CRLF behavior, and byte-for-byte state equivalence are no longer acceptance criteria. Product behavior, versioned run compatibility, safe process execution, and stable machine-readable CLI contracts remain important.

External scripts remain allowed. C++-only means Odin itself ships and runs without Python. The generic executable adapter and project-gate boundaries remain language-neutral. A consuming project may still configure python my_adapter.py, but that interpreter is the project's optional dependency, not Odin's.

02Scope and rules

Required end state

  • One native CLI and workflow engine
  • Native contract validation
  • Native OpenAI-compatible and CLI-agent adapters
  • Native credentials, doctor, and tools commands
  • Native tests and CTest integration drivers
  • No Python configure, install, runtime, or CI dependency

Migration rules

  • Do not modify Python to help the port
  • Add new C++ beside current behavior
  • Test native semantics directly
  • Switch one production boundary at a time
  • Delete replaced Python immediately after its native gate
  • Do not preserve parity-only complexity

06Native replacement details

Contract validation

Implement the subset used by Odin's owned schemas directly over nlohmann::json. The list below was audited against all five files in harness/schemas/ and is exhaustive; implement exactly these seventeen assertion keywords:

type          required      properties    additionalProperties
enum          const         pattern       minLength
items         minItems      maxItems      uniqueItems
minimum       minProperties allOf         if / then
maxItems is required. It appears in agent.schema.json (rules, max 8) and skill.schema.json (procedure, max 10). Earlier drafts of this plan omitted it. Combined with the reject-unknown-keywords rule below, omitting it makes Phase 1 fail to load Odin's own bundled schemas.
  • Load and cache schemas natively. schema_validator owns the harness/schemas path; nothing in C++ resolves it today.
  • Reject unknown assertion keywords instead of silently weakening validation.
  • Allow and ignore the annotation keywords the bundled schemas carry: $schema, title, description. These assert nothing, so they must be on an explicit ignore list rather than triggering the rejection path.
  • Only two regex patterns are used, both plain ASCII (^[a-z0-9][a-z0-9-]{1,63}$ and ^[a-z0-9][a-z0-9-]*$). No $ref, $defs, format, oneOf, anyOf, not, or patternProperties is needed.
  • Pick a defined total order for error sorting. The Python implementation sorts on a path of mixed str and int, which raises TypeError for sibling errors at an object key and an array index of equal depth. Do not reproduce that latent crash.
  • Report useful instance paths; do not reproduce Python wording. tests/cpp/test_contracts.cpp currently pins jsonschema's English message text byte-exactly and must be rewritten in the same change.
  • Remove sidecar from engine, definitions, and contract APIs.

HTTP and adapters

Decided: a narrow in-house HTTP client over a platform split, not a provider SDK and not a vendored TLS stack.

  • Windows: WinHTTP, using the native certificate and proxy stack. No CA bundle to ship.
  • Linux/macOS: libcurl through CURL::libcurl. Adds a CI and packaging dependency; see the risk table.

The client surface stays deliberately small: GET and POST, request headers, request/response body, status code, and a timeout. It must expose the error response body on a non-2xx, because both the OpenAI adapter's diagnostic and discovery's 401/403 handling read it.

discovery additionally needs a raw TCP pre-connect with a sub-second timeout. Python uses socket.create_connection(..., 0.35) so that a closed port costs milliseconds instead of a full HTTP timeout; without it doctor becomes unusably slow. This is a separate small socket helper, not part of the HTTP client.

The OpenAI-compatible adapter must retain semantic behavior: POST /chat/completions, bearer auth, response-format mode, one HTTP 400 retry without JSON mode, tolerant object extraction, bounded diagnostics, and secret redaction. The CLI-agent adapter must retain prompt stdin/argument modes, JSONL text paths, process-tree timeout, and selected credential injection.

Two known Python bugs are not to be reproduced. In openai_compatible.py the 400-retry catches only URLError/OSError, so a second HTTPError escapes as an unhandled traceback. In cli_agent.py the child receives a full os.environ copy rather than the restricted build_child_environment() used everywhere else. The native adapters fix both: catch the second failure, and use the restricted environment.

Credentials and auth

Read existing credential-store version 1 so users do not lose data. Port API keys, imported OAuth fields, expiry checks, masking, environment precedence, and recursive redaction. Use termios and Win32 console mode APIs for no-echo input. Apply 0600 on POSIX and an explicit current-user Windows DACL.

Decided: redaction reproduces all three secret forms. redact_secret replaces the raw secret, its ASCII-escaped JSON form, and its minimally-escaped JSON form, longest form first. Reducing this to the raw form alone would silently stop masking any secret that reaches a log after being JSON-encoded, which is a regression in a security control rather than a simplification. nlohmann can emit both escapings, so this is achievable without reimplementing CPython.

Two Python behaviors are deliberately not carried over. Masking and preview truncation slice by code point in Python; the native versions must also slice on character boundaries, because byte slicing can emit invalid UTF-8 into durable state. And the Windows branch of os.chmod is a documented no-op, so the native DACL is stricter than the implementation it replaces.

Doctor and tools

Port endpoint probing, Ollama tags, hosted-key visibility, executable search, deep model enumeration, text/JSON rendering, and TOML emission. Emitted configuration must use native adapter types and contain no Python path. Keep tool installation explicit and isolated under .odin/tools; use npm for JavaScript tools and uv for Python-implemented third-party tools so Odin itself remains Python-free.

Optional script escape hatch

No Python helper is expected to remain in Odin. If a rare platform task genuinely cannot be ported cleanly, it may temporarily remain an external command invoked through subprocess_run, but it must be optional, excluded from the install by default, and have a named deletion gate. This is an exception mechanism, not the target architecture.

07Migration phases

PHASE 0

Replace parity goals with native scenarios

  • Create C++ helpers for deterministic adapter, gate, and child-process behavior. Concretely: a test_child helper executable (configurable exit code, stdout/stderr volume, sleep, grandchild spawn) and a native mock_agent target.
  • Rewrite test_subprocess.cpp and test_engine.cpp onto those helpers, removing every python -c and python scripts/mock_agent.py fixture.
  • Cover feature, bug-fix, revision, blocked, attempt exhaustion, interruption, malformed handoff, staging, and v1/v2 recovery directly.
  • Keep valid JSON and UTF-8 safety tests; remove Python-specific byte assumptions from future work.
  • Remove the cli-parity step from scripts/gate.py now. It diffs the C++ CLI against the Python CLI, so it starts producing false failures the moment Phase 3 lands native auth. The gate must stop asserting parity before the port begins, not in Phase 6.
  • Stop adding Python parity cases now.

Exit: every material product outcome is asserted by native tests without consulting Python, and no C++ test spawns a Python interpreter for process behavior.

PHASE 1

Native contract validation

  • Add schema_validator and native contract caching, owning the harness/schemas path directly.
  • Implement all seventeen assertion keywords from section 06, including maxItems, and ignore the annotation keywords explicitly.
  • Validate all bundled definitions and task/handoff cases.
  • Rewrite the pinned jsonschema message assertions in test_contracts.cpp against native wording.
  • Remove sidecar ownership from engine and definitions.
  • Replace the odin.py runtime sentinel in runtime_paths.cpp with an installed schema/manifest, and make a missing runtime root a hard error rather than a silent fallback to the build machine's source directory. Moved forward from Phase 5: a silent-wrong-answer failure mode should not survive the phase that removes the file it probes for.
  • Make odin validate --self-only pass with Python absent from PATH.

Delete at exit: sidecar.* and scripts/contract_service.py.

harness/contracts.py and requirements.txt cannot go here. An earlier draft listed them in this phase. They are imported by harness/cli.py, harness/definitions.py and harness/engine.py, so deleting them would break the delegated CLI and the reference engine while both are still in use. contract_service.py is the only validator file with no remaining Python consumer. The other two follow their real owners: the CLI in Phase 5, the reference engine in Phase 7.
PHASE 2

Native extraction, prompts, credentials, and adapters

  • Add native prompt construction and tolerant object/JSONL extraction. Preserve last-balanced-span-wins, candidate ordering, and code-point-safe preview truncation.
  • Add credential-store reading, resolution, masking, and three-form redaction.
  • Add the HTTP client (WinHTTP/libcurl) and the sub-second TCP pre-connect helper.
  • Add built-in openai-compatible and cli-agent adapter types.
  • Keep generic command adapters for arbitrary external executables.
  • Rewrite odin.toml. Point [adapters.mock] at the native mock target from Phase 0, replace the python -m unittest quality gate, and rewrite all three commented adapter examples to native types. Until this lands, the shipped default configuration still cannot run.

Delete at exit: bundled Python adapters, harness/extract.py, and scripts/mock_agent.py.

PHASE 3

Native auth commands

  • Add CLI11 subcommands for set, list, remove, and import.
  • Implement secure input and native file permissions.
  • Retain compatibility with existing credential-store version 1.

Exit: all auth operations and error paths pass native CLI tests.

PHASE 4

Native doctor, discovery, and tools

  • Port HTTP and Ollama model parsing, endpoint probes, executable discovery, and deep CLI enumeration.
  • Emit native adapter TOML only.
  • Port explicit npm/uv tool installation and binary verification.

Exit: doctor and tools work from the native CLI with no delegated process.

PHASE 5

Remove delegation and finish native CLI ownership

  • Delete the leading-command delegation branch.
  • Move large handlers out of cli.cpp into command modules.
  • Remove ODIN_PYTHON and all Python guidance. (Runtime asset detection was already moved off odin.py in Phase 1.)

Delete at exit: delegate.*, odin.py, and harness/cli.py.

PHASE 6

Native CI, integration, and packaging

  • Replace Python gate and integration drivers with C++ test/helper executables.
  • Remove Python setup, pip, corpus generation, and Python test steps from CI.
  • Remove Python files from CMake install rules and Python discovery from configure.
  • Run clean Windows/Linux configure, build, CTest, install, interruption, and installed-layout tests without Python.

Exit: install prefix contains no Python and all CTest entries are native.

PHASE 7

Delete all remaining Python and parity artifacts

  • Delete every tracked .py file.
  • Delete Python engine/CLI/config/discovery/credential tests and parity scripts.
  • Delete test_engine_parity.cpp, test_json_parity.cpp, and the CPython byte corpus.
  • Remove Python-emulation comments and rename tests around product requirements.

Exit: repository, build graph, CI, install tree, and documentation are C++-only.

The migration ends at Phase 7. Every acceptance criterion in section 11 is satisfiable without the work below. It is tracked separately so that it does not inflate the apparent scope or the schedule of the port.

07bAfter the port: architecture cleanup

Not part of the C++-only migration. This is ordinary design work that becomes possible once there is one implementation instead of two, and it should be scheduled and estimated on its own.

  • Extract stage execution and Git mechanics from engine.cpp into stage_executor.
  • Extract validation and benchmark code from cli.cpp.
  • Isolate benchmark workspaces so profiles stop sharing one mutable project tree.
  • Add graceful cancellation, progress/follow output, run listing, and capability-aware routing.
  • Enforce or remove agent reads/writes and skill output declarations.

Exit: C++ module ownership is clear and product definitions describe enforced behavior.

11Final acceptance criteria

  • The repository contains no tracked .py files.
  • No C++ test spawns a Python interpreter, including as a generic child-process fixture.
  • CMake does not discover, invoke, or install Python.
  • Windows and Linux configure, build, test, and install without Python available.
  • The install prefix contains no .py, .pyc, Python package, or requirements file.
  • The checked-in odin.toml runs end to end with no Python on PATH, including its default routing profile and quality gate.
  • Runtime asset resolution fails loudly when the runtime root is missing rather than falling back to a build-time source path.
  • validate, start, resume, status, benchmark, models, doctor, auth, and tools are native.
  • Native OpenAI-compatible and CLI-agent adapters cover extraction, credentials, redaction, timeout, and process-tree cleanup.
  • Existing credential store v1 remains readable.
  • Supported run-state versions remain semantically readable.
  • doctor --emit-config emits no Python or .py command.
  • Generic executable adapters and project gates remain supported in any user-chosen language.
  • Installed-layout and interruption tests are native CTest entries.
  • CI contains no Python setup, pip, Python test, or parity step.
  • README contains no Odin Python-runtime instructions.
