User Stories

What people actually need from Odin, written as outcomes rather than features.

Each story carries acceptance criteria. A criterion that cannot be checked is a wish, not a criterion.

Who Odin is for

The maintainer

Owns a C++ codebase and wants agent work to arrive as reviewable, gated changes rather than as a chat transcript.

The evaluator

Has several models available and needs evidence about which is worth paying for on this codebase.

The integrator

Is building a tool, GUI, or pipeline on top of Odin and needs stable, machine-readable contracts.

The stories

US-001   Run a task to a reviewable change Maintainer · hand Odin a task and get a gated, staged change back US-002   Resume after an interruption without duplicate work Maintainer · a crash mid-run must not silently repeat external effects US-003   Link a model without guessing its name Maintainer · discover what this machine can actually reach, then configure it US-004   Use a provider key without leaking it Maintainer · store a secret once; never see it in argv, logs, or state files US-005   Compare models on evidence, not vibes Evaluator · score models on whether the work was actually done US-006   Drive Odin from a front-end Integrator · watch a run live without linking to Odin's ABI
Not all of this exists yet. US-005 describes the outcome the testable examples plan is designed to deliver; today's benchmark measures completion, not correctness. Each story marks its own status.
