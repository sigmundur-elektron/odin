US-005   Compare models on evidence, not vibes

Evaluator · PARTIAL — see the examples plan

The story

As an

evaluator choosing between a local 32B model and a hosted frontier model, I want to run the same task through both and compare whether the work was actually done, so that I can justify the cost difference with evidence from my own codebase rather than a public leaderboard.

Why today's answer is wrong

The benchmark currently measures the wrong thing. It records status, transitions, duration and model metadata. A model that replies {"status":"approved"} to every stage without writing a single line of code produces a perfect run in a shorter time than one that did the work. Worse, all profiles share one mutable workspace in sequence, so the second model starts from the first one's edits.

Both problems have the same root cause: nothing checks the result. The verify stage emits a criteria artifact that no code reads.

What it should do

Acceptance criteria

  1. Each profile runs against its own copy of the seed workspace; no profile can observe another's edits.
  2. Every profile is evaluated by the same acceptance checks, declared by the example rather than by the model.
  3. Acceptance checks are never shown to the model. The marking scheme does not enter the prompt.
  4. At least one check per example is objective — a build or a test suite — rather than a text match.
  5. The report records which individual checks passed and failed, not only a total.
  6. The report retains status, transitions and duration, so a model that reached the same result in fewer attempts is visible as such.
  7. A model that reports success without changing the workspace scores zero on the objective checks.
  8. The example is proven satisfiable by a deterministic scripted run, so a low score means the model failed rather than that the example was impossible.
  9. Output states the sample-size caveat: one task is evidence, not a ranking.
Design and phasing: see the testable examples plan, which exists to deliver this story.
