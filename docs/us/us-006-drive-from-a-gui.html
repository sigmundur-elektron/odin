US-006   Drive Odin from a front-end

Integrator · PARTIAL

The story

As a

developer building a GUI on top of Odin, I want to spawn it as a child process and watch a run progress by reading files, so that I do not have to link against its C++ ABI or keep my UI in lockstep with its internals.

The model is Git: a GUI adds workflows on top without replacing the tool underneath. Odin's public contract is its CLI and its run directory, not odin_core.

The integration surface

Acceptance criteria

  1. doctor --json and models --json emit machine-readable output suitable for populating a picker.
  2. start emits the run directory and final state as JSON on stdout.
  3. Run state is durable on disk in documented locations, readable while the run is in progress.
  4. Every state file is written by atomic replacement; a reader never observes partial JSON and needs no lock.
  5. Per-stage events appear as individually numbered files, so a watcher can render progress incrementally.
  6. Exit codes are stable and documented: 0 success, 1 nothing found, 2 failure.
  7. A front-end needs no compilation against Odin; spawning the executable is sufficient.
Gaps. There is no odin runs listing command, no progress or follow mode, and no graceful cancellation — a front-end must enumerate the run directory itself and kill the process to stop it. These are listed as post-migration work.

Design notes

Why files rather than a server. A filesystem contract needs no port, no authentication, no protocol version, and survives the front-end being closed and reopened. An odin serve control plane is only worth adding if a GUI outgrows spawning the CLI.
