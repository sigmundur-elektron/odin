US-001   Run a task to a reviewable change

Maintainer · SHIPPED

The story

As a

maintainer of a C++ codebase, I want to hand Odin a described task and get back a change that has already passed my own quality gate, so that I review working code instead of reading a chat transcript and copying snippets out of it.

The distinction that matters: an agent chat produces suggestions, and the human is the integration step. Odin produces a change plus evidence — the gate output, the stage history, and an explicit list of files touched.

What happens

odin start examples/feature.json

The command creates a durable run under .odin/runs/<run-id>/, executes the state machine, and stops at complete or blocked. Nothing is committed or pushed; the implementer's changed_files becomes a staging manifest, and automatic git add is opt-in.

Acceptance criteria

  1. Given a task file that satisfies task.schema.json, when I run odin start, then a run directory is created containing task.json, state.json, context.json, and a per-stage event log.
  2. The configured project gate is executed with its exact command, and its exit code and output are recorded as a gate artifact.
  3. A non-zero gate returns the run to implementation rather than accepting the change.
  4. Repeated failure ends the run as blocked within the configured transition budget, never in an unbounded loop.
  5. On success the process exits 0; a run that ends blocked exits 2.
  6. The reported changed_files are project-relative, normalised, unique paths inside the project root; absolute paths, traversal, and directories are refused.
  7. Nothing is committed or pushed. Staging happens only when git.stage_on_success is enabled, and then only with literal pathspecs.
  8. An invalid task is rejected before a run directory is created, naming the offending field.

Design notes

Why a gate the project owns. Odin prescribes no build system or test framework. The gate is whatever command the repository already trusts, so "passed the gate" means the same thing to Odin as it does to the team.
Known gap. The verify stage produces a criteria artifact that nothing reads — the verifier's verdict is currently an unchecked opinion. Turning acceptance criteria into enforced checks is the subject of the testable examples plan.
