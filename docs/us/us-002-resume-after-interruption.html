US-002   Resume after an interruption without duplicate work

Maintainer · SHIPPED

The story

As a

maintainer whose laptop closed mid-run, I want to resume without silently repeating work whose external effect I cannot see, so that I am never billed twice for the same call or left wondering whether a stage ran once or twice.

The hard case is not a crash between stages — that is just bookkeeping. It is a crash during a stage, after the model was called but before the result was committed. Odin cannot know whether the provider processed that request.

The uncertainty window

Plain resume refuses and explains. Acknowledging a possible duplicate effect is an explicit act:

odin resume <run-id>                      # blocked: outcome uncertain
odin resume <run-id> --retry-interrupted  # yes, run it again

Acceptance criteria

  1. A stage attempt is journaled and persisted before the adapter or gate is invoked, so an interruption is always detectable.
  2. A second process attempting to resume a run that is already executing is refused with exit 2 and a message naming the conflict.
  3. After an interruption inside the uncertainty window, plain resume ends the run with reason_code: outcome_uncertain and exits 2.
  4. Plain resume does not re-invoke the interrupted stage; the external invocation count is unchanged.
  5. resume --retry-interrupted executes a new attempt and can carry the run to complete.
  6. State files are replaced atomically, so a reader never observes partial JSON regardless of when the process died.
  7. Journal records are immutable and append-only; recovery reconciles from them rather than from mutable state alone.

Design notes

Why refuse rather than guess. Both silent choices are wrong. Silently replaying may duplicate a paid call or a side effect; silently skipping may lose completed work. Odin makes the ambiguity visible and lets the person who can check the provider decide.
Covered by an end-to-end test. odin_interruption_smoke starts a real run, kills Odin mid-attempt, kills the stranded child, and asserts every criterion above — including that the invocation count does not change on plain resume.
