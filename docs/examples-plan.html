Testable Examples

Make examples/ prove something, so that benchmarks can measure something.

Plan only · nothing here is implemented · 2026-09-02

01The problem, as measured

Odin ships three example tasks. Every one of them is an input with no corresponding expected outcome, and nothing runs them.

ClaimEvidence
examples/ is not testedReferenced only by three lines of README.md. No CTest entry, no CI step, no test source mentions it.
A run of an example proves the state machine, not the exampleThe built-in mock adapter reads only agent.id and task.request. Every other field in frontend-gui.json — all five constraints, all six acceptance hints — is never read by anything.
Nothing enforces acceptance criteriaThe verifier stage emits a criteria artifact. Grepping src/ for criteria finds only the mock that produces it. No code ever reads it. The verifier's verdict is unchecked opinion.
Benchmark cannot distinguish a good model from a bad onecli_benchmark records status, transitions, duration_seconds, and model metadata. A model that returns {"status":"approved"} to every stage without writing a single line of code scores a perfect run.
Benchmark results are not comparableEvery profile runs against the same mutable project directory, in sequence. Profile two inherits profile one's edits. README.md already says so: "Treat results as diagnostic, not fair comparative evidence."
The sharpest way to put it. odin benchmark examples/feature.json --models a b c currently measures how fast three models can say the word "approved". That is the gap this plan closes, and it is why examples and benchmarking are the same problem rather than two.

02The core insight

There is an apparent conflict between the two things wanted from an example:

Testable in CI

Must be deterministic, offline, fast, and free. That rules out calling a real model.

Useful for benchmarking

Must call a real model, whose output is by definition not deterministic.

The resolution is that these differ only in who produces the handoffs. Everything else — the task, the starting workspace, the quality gate, and above all the definition of success — is identical.

One bundle, one definition of success, two adapters. An example declares its own acceptance checks. A scripted adapter runs them deterministically in CI to prove the example and the checks are themselves correct. A real model runs the same checks to produce a benchmark score. The checks are the shared artefact, and they are what turns "the workflow completed" into "the work was actually done".

03Example bundles

An example becomes a directory rather than a bare JSON file. The task input keeps its current shape and moves inside.

examples/add-export-command/
  task.json        the Odin task input, unchanged in shape
  workspace/       the starting project the agent is asked to modify
  expect.json      what must be true when the run finishes
  script.json      recorded handoffs, for the deterministic run
  odin.toml        adapter, gate and routing for this example
  README.md        what this example demonstrates, for a human
Expectations must never reach the agent. The task already carries acceptance_hints, which the model is allowed to see. expect.json is the marking scheme and is loaded only by the evaluator. Passing it into the prompt would let a model satisfy the checks by echoing them rather than by doing the work — and would make every benchmark score meaningless.

Backward compatibility

Bare examples/feature.json keeps working as a task input; the README commands do not break. A directory is simply recognised as a bundle when it contains task.json. Existing examples are converted, not deleted.

04Expectations

Declarative, because the same file is read by a CTest assertion and by a scoring run, and because a check written in C++ could not be added by a consuming project.

{
  "checks": [
    { "id": "builds",
      "kind": "command",
      "command": ["cmake", "--build", "build"],
      "exit_code": 0,
      "weight": 3 },

    { "id": "tests-pass",
      "kind": "command",
      "command": ["ctest", "--test-dir", "build"],
      "exit_code": 0,
      "weight": 3 },

    { "id": "export-command-exists",
      "kind": "file_matches",
      "path": "src/main.cpp",
      "pattern": "export" },

    { "id": "import-format-untouched",
      "kind": "file_unchanged",
      "path": "src/import.cpp" },

    { "id": "run-completed",
      "kind": "run_status",
      "status": "complete" },

    { "id": "no-thrash",
      "kind": "max_transitions",
      "value": 20 }
  ]
}
KindAssertsWhy it earns its place
commandA command run in the finished workspace exits as expected.The only genuinely objective check. Compiling and testing is what separates working code from plausible code.
file_exists / file_absentA path is or is not present.Catches a model that reports success without creating anything.
file_matchesA file's contents match a regular expression.Cheap structural evidence when a full build is too slow. Use sparingly; it rewards keyword stuffing.
file_unchangedA file is byte-identical to the seed workspace.Encodes a constraint as a check. "Do not change the existing import format" is currently unenforceable.
staged_filesThe set Odin reported matches an expected set.Tests Odin's own staging contract, not the model.
run_statusThe run ended complete or blocked.Some examples should deliberately end blocked; that is a pass, not a failure.
max_transitionsThe run settled within a budget.Distinguishes a model that solved it from one that thrashed to the same answer.
Weights are for scoring, not for passing. In conformance mode every check must pass. In benchmark mode the weighted fraction becomes the score, so "builds" can count for more than "mentions the word export".

05Two run modes

ConformanceBenchmark
Adaptertype = "scripted"a real model profile
Determinismtotalnone
Networknoneusually
Runs in CIyes, every pushno, on demand
Failure meansOdin, the example, or the checks are brokenthe model did not do the work
Resultpass / failweighted score plus duration and transitions

The conformance mode is what makes the benchmark trustworthy. Without it, a low benchmark score is ambiguous: it could mean the model failed, or it could mean the example was unsatisfiable and nobody noticed. Proving the bundle is passable with known-good handoffs removes that ambiguity.

06Workspace isolation

Each run copies workspace/ to a scratch directory and executes there. This is a prerequisite, not a nicety:

  • Repeatability. A conformance test that mutates its own fixture passes once and then fails, or worse, keeps passing for the wrong reason.
  • Comparability. Benchmark profiles currently share one directory in sequence, so the second model starts from the first one's edits. Any comparison between them is invalid, which the README already concedes.
  • Parallelism. Isolated runs can eventually run concurrently; shared ones never can.

This closes the "Isolate benchmark workspaces" item already listed as post-migration work in the C++-only plan. It is pulled forward here because examples cannot be tested without it.

Git is a complication worth deciding early. Odin's staging step requires the project root to be a Git worktree root. A copied workspace either needs git init per run, or examples that exercise staging must be marked as requiring it. Cheap either way, but it must be chosen rather than discovered.

07The scripted adapter

A fourth built-in adapter kind, alongside mock, openai-compatible and cli-agent. It replays recorded handoffs keyed by stage, and applies the file edits a real model would have made.

[adapters.scripted]
type = "scripted"
script = "script.json"
{
  "specify": { "status": "approved", "summary": "...", "artifacts": { ... } },
  "implement": {
    "status": "approved",
    "summary": "added the export command",
    "artifacts": { "changed_files": ["src/export.cpp", "src/main.cpp"] },
    "writes": {
      "src/export.cpp": "@file:fixtures/export.cpp",
      "src/main.cpp":   "@file:fixtures/main.cpp"
    }
  }
}

The writes map is the part mock does not have and cannot have. A conformance run must leave a workspace that genuinely compiles, or the command checks prove nothing. @file: keeps real source in real source files rather than escaped into JSON.

Why not record from a real model? Tempting, and possible later as odin example record. Starting with hand-written scripts is better: a recorded script bakes in whatever a particular model happened to do, including its mistakes, and a conformance fixture should encode the intended solution.

08Benchmark scoring

benchmark gains the expectation result per profile. The report keeps its current fields and adds:

{
  "profile": "coder-32b",
  "status": "complete",
  "transitions": 9,
  "duration_seconds": 412.7,
  "score": { "passed": 5, "total": 6, "weighted": 0.82 },
  "checks": [
    { "id": "builds",      "passed": true },
    { "id": "tests-pass",  "passed": true },
    { "id": "no-thrash",   "passed": false, "detail": "24 transitions, budget 20" }
  ]
}

This is the difference between "three models all finished" and "two produced code that builds, one of them on the first attempt". Cost and token metrics, already listed as future work in the README, slot into the same record later.

A score is not a ranking. One task cannot rank models, and a suite of six is still a small sample. The honest framing is per-check evidence, and the report should preserve which checks failed rather than collapsing to a single number. Whether to print a headline percentage at all is a decision below.

09The example set

Six bundles, chosen so that each proves something the others do not. Small enough that the whole suite is a CI step, not a nightly job.

BundleKindWhat it proves
add-export-commandfeatureThe happy path end to end: a real C++ file is added, the project builds, tests pass. The baseline every other example varies from.
fix-empty-path-crashbugfixThe bug-fix workflow, including the regression checkpoint. Ships with a failing test that must pass afterwards — the cleanest possible objective check.
respect-constraintfeatureA constraint is enforced by file_unchanged. A model that solves the task by rewriting the forbidden file scores zero despite "succeeding".
gate-forces-revisionfeatureThe gate fails on the first attempt, so the run must loop back to implement and recover. Exercises revision transitions, which no current test covers end to end.
impossible-requestfeatureExpects run_status: blocked. Proves Odin refuses cleanly rather than looping, and catches a model that fabricates success.
frontend-guifeatureThe existing large example, kept as a benchmark-only bundle. Too slow for CI; it is where model capability actually separates.
CI runs the small five. frontend-gui is marked benchmark_only. Building an OpenGL and ImGui application on three platforms per push is not a reasonable CI cost, and its value is as a capability probe rather than a regression test.

10Phases

PHASE 1

Workspace isolation

  • Copy a seed workspace to a scratch directory per run; run there.
  • Decide and implement the Git question from section 06.
  • Give benchmark a fresh workspace per profile.

Exit: two benchmark profiles on one task cannot observe each other's edits, proven by a test that would fail today.

PHASE 2

Expectations evaluator

  • expectations.h/.cpp: parse expect.json, evaluate against a finished workspace and run state, return per-check results.
  • Native tests for every check kind, including each one's failure path.
  • Reuse the existing schema validator to validate expect.json itself.

Exit: every check kind passes and fails for the right reason, with no example bundle in existence yet.

PHASE 3

The scripted adapter

  • Add type = "scripted" with stage-keyed handoffs and writes.
  • Path safety on writes: reuse the staging rules, so a script cannot write outside the workspace.

Exit: a scripted run produces a workspace that differs from the seed in exactly the declared way.

PHASE 4

Bundle format and runner

  • Bundle discovery and loading; bare .json examples keep working.
  • odin example run <dir> and odin example list.
  • Convert the three existing examples into bundles.

Exit: odin example run examples/add-export-command passes, and fails if a check is deliberately broken.

PHASE 5

CI integration

  • A CTest entry per bundle, so a failure names the example.
  • Write the remaining bundles from section 09.

Exit: ctest runs every non-benchmark example on every push, on both platforms.

PHASE 6

Benchmark scoring

  • Evaluate expectations after each profile; record per-check results in the report.
  • odin benchmark <bundle> --models a b c.
  • Update the README to stop describing benchmark output as merely diagnostic.

Exit: a benchmark distinguishes a model that produced building code from one that only claimed to.

11Risks

RiskControl
Examples become a slow CI step and get disabledSeed workspaces stay tiny and self-contained. The one genuinely heavy example is benchmark-only. Budget: the whole suite under a minute.
The conformance script drifts from what a real model would produce, so the example only proves the scriptAccepted and explicit: conformance proves Odin and the checks, not the model. The benchmark mode is what exercises reality.
file_matches checks reward keyword stuffingPrefer command checks. Treat a bundle whose checks are all regex as a smell during review.
A seed workspace needs a toolchain CI does not haveSeeds build with the compiler already required to build Odin. No new dependency for an example.
Scoring invites over-reading a small sampleReport per-check results, not just a number. Document the sample-size caveat next to the output.
Bundle format churn breaks consuming projectsVersion expect.json from the first commit, and validate it with the existing schema validator rather than ad-hoc parsing.

12Decisions needed before implementing

  1. Git in isolated workspaces. git init every scratch workspace, or mark staging-dependent examples and skip staging elsewhere?
  2. Command surface. A new odin example command, or fold conformance into a native odin_examples test target and leave the CLI unchanged?
  3. Headline score. Print a single weighted percentage, or per-check results only? A number is easier to act on and easier to misuse.
  4. Seed workspace build system. CMake, matching Odin's own gate, or a plain compiler invocation to keep examples toolchain-light?
  5. Scope now. Phases 1–2 are useful on their own — workspace isolation is a real bug fix and the evaluator is independently testable. Worth landing those first and reviewing before the format is settled?
