Compare models

Run one task across several profiles — and understand the limits of the result.

1Run a benchmark

odin benchmark examples/feature.json --models coder-32b coder-80b frontier

Each profile gets a fresh run directory. Results land under .odin/benchmarks/, named by local timestamp and task id.

Model size is descriptive metadata, not a threshold. To try one profile without a full comparison:

odin start task.json --model coder-32b

2Read the report

Recorded per profile: completion status, transition count, wall-clock duration, and model metadata.

FieldMeans
statuscomplete or blocked.
transitionsStage transitions used. Higher means more revision loops.
duration_secondsWall clock, including your gate.
run_dirWhere to read the full history for that profile.

The most informative field today is transitions: two models that both reached complete, one in 8 transitions and one in 22, did not perform equally.

3What the numbers do not mean yet

Benchmark results are currently diagnostic, not comparative evidence. Two limitations, both real:
  • Nothing checks the work. Status, transitions and duration are all satisfied by a model that replies "approved" to every stage without writing any code — and it will look faster than one that did the work.
  • Profiles share one workspace. They run sequentially against the same project directory, so the second model starts from the first one's edits.

Until that is fixed, treat a benchmark as a smoke test — "can this model complete the workflow at all, and how much did it thrash" — rather than as a ranking. Read the run directories; do not rely on the summary alone.

Being worked on. The testable examples plan adds isolated workspaces per profile and declarative acceptance checks, so a benchmark can score whether the code actually builds and passes tests. See also US-005.
