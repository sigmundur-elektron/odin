Recover an interrupted run

Resume safely, and understand when Odin needs you to decide.

1Find the run

ls .odin/runs/
odin status <run-id>

status never modifies anything and always exits 0. Read state.json for status, current_stage, stage_attempts and, if present, in_progress.

There is no odin runs listing command yet. Enumerate the state directory directly.

2Resume

odin resume <run-id>

If the interruption happened between stages, the run simply continues. That is the common case and needs nothing from you.

3When the outcome is uncertain

Each attempt is journaled and persisted before external work begins. If a process stopped after an attempt started but before completion was committed, Odin cannot know whether the adapter actually ran — the model may have been called and billed.

Plain resume refuses rather than guessing:

$ odin resume 20260902-084251-add-export-command-fa68ed
{ "state": { "status": "blocked", "reason_code": "outcome_uncertain", ... } }
exit 2

Nothing was re-executed. Decide, then acknowledge explicitly:

odin resume <run-id> --retry-interrupted
SituationDo
Local model, no cost, no side effectsRetry. Duplication is harmless.
Paid providerCheck the provider's usage first if a duplicate call matters, then retry.
The stage had external side effects beyond the modelInspect the workspace before retrying.
You want to abandon the runDelete the run directory. Nothing outside it is affected.
Why not decide automatically. Both silent choices are wrong: replaying may duplicate a paid call, skipping may lose completed work. Odin makes the ambiguity visible to the person who can check.

4"Already being executed"

odin: run <id> is already being executed
exit 2

An OS-backed lock at .odin/runs/<id>/run.lock prevents two processes touching one run. Either another process really is running it — check first — or a previous process died without releasing the lock, in which case the lock clears once that process is gone.
