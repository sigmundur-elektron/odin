Run your first task

From an empty project to a gated, reviewable change.

1Configure the project

Odin needs three things: somewhere to keep run state, a quality gate, and a model to route work to. The smallest working odin.toml:

[harness]
state_dir = ".odin/runs"
max_total_transitions = 40

[git]
stage_on_success = false

# Your gate. Odin prescribes no build system or test framework.
[gates.quality]
command = ["ctest", "--test-dir", "build", "--output-on-failure"]
timeout_seconds = 300

# The built-in deterministic mock: proves the mechanics with no model.
[adapters.mock]
type = "mock"

[models.mock]
adapter = "mock"
model = "deterministic-contract-fixture"

[routing]
default = "mock"
Start with the mock. It returns fixed handoffs and never calls a provider, so your first run proves your gate and your paths are right before a model is involved. Swap routing.default to a real profile once it works.

Check what Odin understood:

odin validate
odin models

2Write a task

A task is ordinary JSON validated against task.schema.json before a run starts.

{
  "id": "add-export-command",
  "kind": "feature",
  "title": "Add an export command",
  "request": "Add a command that exports the active document as JSON.",
  "context": { "entry_point": "src/main.cpp" },
  "constraints": ["Do not change the existing import format."]
}
FieldRequiredNotes
idyesLowercase, 2–64 chars, a-z 0-9 -. Becomes part of the run directory name.
kindyesfeature or bugfix. Selects the workflow.
titleyesOne line.
requestyesWhat to do and why. The single most load-bearing field.
reproductionfor bugfixRequires steps, expected, actual.
contextnoFree-form. Anything the agent should know.
constraintsnoWhat not to do.

Templates for both shapes ship in share/odin/harness/templates/.

3Run it

odin start task.json

Override a field without editing the file, or pick a different profile:

odin start task.json --set title="Different title"
odin start task.json --model coder-32b
--set values are strings. --set count=1 stores "1", not 1. Validation runs after the override is applied, so a type mismatch is caught before the run starts.

4Read the result

Run state lives under .odin/runs/<run-id>/:

task.json       immutable validated request
state.json      current stage, status, attempts, transition count
context.json    artifacts and complete event history
events/*.json   per-stage handoffs
journal/*.json  immutable stage-started and stage-completed records
run.lock        OS-backed per-run execution lock

Inspect without changing anything:

odin status <run-id>

A run ends complete or blocked. blocked exits 2 and means a stage exhausted its attempts, or the transition budget ran out. The reason is in state.json and the last events.

5Staging

The implementer reports changed_files. The final stage copies those paths into a staging manifest. Automatic git add is opt-in:

[git]
stage_on_success = true
timeout_seconds = 300

Paths must be unique, normalised, project-relative and use /. Absolute paths, traversal, directories and anything resolving outside the project root are refused. Staging requires the project root to be the Git worktree root, uses literal pathspecs, and verifies the exact file set afterwards.

Odin never commits or pushes. The most it will do is stage the exact files it was told about.
