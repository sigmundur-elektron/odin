Odin Durable Run Format

State schema v2 and the interruption-recovery contract.

Directory layout

.odin/runs/<run-id>/
  task.json                 validated input
  context.json              completed artifacts and handoff history
  state.json                current workflow and active attempt
  run.lock                  persistent file; ownership is an OS lock
  events/NNN-stage.json     completed-handoff compatibility projection
  journal/*-started.json    immutable attempt intent
  journal/*-completed.json  immutable completion commit

Commit protocol

  1. Acquire the OS-backed per-run lock.
  2. Publish an immutable stage_started record.
  3. Persist the incremented attempt and in_progress state.
  4. Execute the agent, gate, checkpoint, or staging operation.
  5. Validate and publish an immutable stage_completed record.
  6. Publish the completed event, then update context and state snapshots.
Commit point: a stage_completed journal record proves that Odin may repair snapshots without executing that stage again.

Interruption behavior

A started record without a matching completion means the external outcome is uncertain. Odin does not silently replay it. Plain resume records reason_code: outcome_uncertain and blocks. The operator can acknowledge possible duplicate external effects with:

odin resume <run-id> --retry-interrupted

The uncertain attempt remains consumed. A retry receives a new execution ID and the next attempt number.

Compatibility projections

context.history and events/NNN-stage.json continue to contain completed handoffs only. Existing GUI and tooling consumers can keep using them. New consumers may use state.in_progress and the journal for immediate attempt progress and recovery diagnostics.

Schema versions

VersionBehavior
1Readable for compatibility. A nonterminal v1 run has no durable attempt intent, so resume treats its current outcome as uncertain.
2Uses immutable started/completed journal records and persisted in_progress state.
FutureRejected until a reader or migration is implemented.

Locking

The existence of run.lock does not mean a run is active. Odin holds a kernel lock on that persistent file while executing. Process termination releases ownership automatically, avoiding stale PID-file deletion rules. This protects one run from concurrent resume; separate runs can still affect a shared workspace until workspace isolation is implemented.

Durability scope

Journal publication is create-only and atomically exposes complete JSON. State and context are replaceable snapshots. The protocol makes ordinary process interruption diagnosable and recoverable. Exact-once external side effects remain impossible without adapter cooperation, so unmatched starts require explicit operator acknowledgement.
