01What Odin is

A durable JSON state machine that drives an agent pipeline. A task runs through a workflow of stages; each stage emits a handoff/v1 object with status approved, revision or blocked, and the workflow routes on that. Everything is written to .odin/runs/<id>/ through atomic temp+rename, so an external reader (a planned ImGui GUI) can poll without locking.

Odin bundles no model provider and no AI framework. An adapter is any executable that reads one JSON request on stdin and writes one handoff on stdout. That process boundary is the whole extension mechanism — and it is why the port is a hybrid rather than a rewrite.

C++ never touches a secret. Adapters resolve their own credentials from a name; secrets never appear in argv. Because auth is forwarded to Python, the C++ binary has no secret-handling code at all.

Three defects the parity work caught

  • State files are CRLF on Windows. Python writes them in text mode, so every \n from json.dump becomes \r\n. Would have broken parity on every file.
  • UTF-8 replacement was wrong. CPython follows the Unicode maximal subpart rule, so b"\xe0\x80\xaf" yields three U+FFFD, not one. Gate output goes straight into state files.
  • reproc does not kill process trees. adapters/cli_agent.py launches the real agent CLI as a grandchild; a timeout would have stranded it. Fixed with a Windows job object.

Known divergences deliberate, documented in source

  • JSON key order on start/benchmark/validate stdout — Python uses sort_keys=False, the port sorts. No semantic difference; state files are sorted on both sides.
  • Parse-error text for malformed JSON/TOML differs. Only reachable on a corrupt hand-edited file.
  • {model} and {task_file} expansion uses plain substitution, not str.format, so a stray { no longer raises.
  • Timeouts kill the whole process tree; subprocess.run only waits for the direct child.

04What is missing

Port gaps

SevGap
HIGHPOSIX has never been compiled or run. Every #ifdef branch for Linux/macOS — fork/execvp delegation, rename, gmtime_r, the no-op job object — is unverified. The parity corpus is also Windows-only (CRLF); it must be regenerated per platform.
HIGHNo CI. Nothing runs the gate automatically. Note that git is not on PATH on this machine — it exists only bundled inside VS — which will bite any runner setup.
MEDDormant Python cannot be removed yet. harness/cli.py imports config, definitions, engine and adapters at module scope, so deleting them breaks odin.py and therefore doctor/tools/auth. Split cli.py first. Recommendation: keep them regardless — they are the parity oracle.
MEDNo standalone install path. Definitions, the sidecar script and odin.py are all located via config.root. Fine while tool and project coincide; broken the moment odin.exe is installed elsewhere.
LOWBuild script lives outside the repo; the VS 2026 CMake/Ninja/git paths are not on PATH.

Product gaps observed while porting, not port-related

SevGap
HIGHA run is silent. Nothing is printed until it finishes, yet an agent stage can take minutes. For a tool whose entire job is supervising slow agents, this is the biggest usability hole. Event files are already written per stage, so a --follow or progress line is cheap.
HIGHbenchmark is not a fair comparison. Each model gets its own run directory, but all of them mutate the same working tree in sequence. Model N sees the changes model N−1 made. Needs an isolated tree (worktree, copy, or a clean checkout) per profile.
MEDNo cancellation. Ctrl-C mid-run has undefined behaviour: no signal handling, no final state write. The run is left running forever and resume will re-execute the interrupted stage.
MEDFull environment is handed to every child. Gates and adapters inherit all of os.environ, including any provider keys. There is no allowlist, which undercuts the otherwise careful secret handling.
MEDCredentials are plaintext JSON. 0600 on POSIX, but on Windows it relies on NTFS ACL inheritance with no chmod equivalent. No DPAPI / Keychain / libsecret.
LOWschema_version is written but never read — no migration path exists.
LOWNo way to list runs. Inspecting history means ls on .odin/runs/ and reading JSON by hand. An odin runs command is the obvious companion to status.
LOWgit add runs with no timeout (inherited from the Python original).
For whoever writes the GUI. The atomic-write contract exists but nothing consumes it yet. On Windows, MoveFileEx fails if a reader holds the target open — a polling GUI must open state files with FILE_SHARE_DELETE or it will block the engine's writes. The engine retries 5× at 10 ms, then reports an error.

05Recommended order

  1. Build and run the gate on Linux. Highest risk, lowest cost. Regenerate the parity corpus there and the differential tests will tell you immediately what is wrong.
  2. Add run progress output. Small change, largest usability return.
  3. Wire CI around scripts/gate.py on both platforms.
  4. Isolate benchmark runs, or document that benchmark is sequential and not comparative.
  5. Decide the install model (bundled vs standalone), which unblocks path resolution and packaging.
  6. Signal handling and cancellation.

Deleting the Python originals is not on this list. Keeping them costs ~700 dormant lines and buys a working oracle that runs on every gate.
